# CLI·TUI 최적화와 전후 비교 — 2026-10-23

## 적용 내용

공통 Driver → DB 검사 재사용 → TUI 갱신 순서로 적용했다.
기준 소스는 `603bc74b1e1b65eb9bee823e4b20fbad2c9ebadb`의 driver.py, kakaodb.py, tui.py다.
세 파일의 변경 전 사본이 이 커밋과 같음을 확인하고 동일한 기기/fixture에서 비교했다.

### Driver

- 준비 상태를 즉시 확인하고, 미완료일 때 100→200→400→최대 600ms로 간격을 늘린다.
  시간 계산은 monotonic을 사용하고 남은 시간보다 오래 sleep하지 않는다.
  개별 ADB 호출 시간 제한은 별도이며 이 값이 전체 호출 시간의 절대 상한은 아니다.
- 대화 목록은 Chats 탭·All 필터 선택 상태와 목록 노드를 확인한다.
  이미 선택한 탭/필터를 다시 누르지 않으며 같은 XML의 확인 결과를 재사용한다.
- 자기채팅 진입, 앱 실행 뒤의 불필요한 정착 대기, 문서 선택기의 화면 전환 대기를
  다음 화면의 selector/focus 확인으로 바꿨다. 목록 재조회 마지막의 500ms sleep도 없앴다.
- 텍스트 입력은 포커스, 입력 문자열 반영, 활성화된 전송 버튼을 확인한 뒤 한 번만 제출한다.
  기존 동일 본문이나 아직 입력란에 있는 초안만으로 송신 성공을 확인하지 않는다.
  표시된 메시지의 일치 개수가 이전보다 증가해야 확인되며, 전송 후 dump 오류/확인 실패는
  `send_uncertain`이다. 자동 재전송하지 않는다. 중복 본문이 화면에서 밀려나 개수가 늘지 않는
  경우 실제 송신됐어도 uncertain일 수 있으므로 사용자가 확인해야 한다.
- 파일 전송 후 완료를 확인할 확실한 조건이 없는 기존 대기와 복구용 대기는 유지했다.
  이 변경이 모든 고정 sleep을 제거하거나 파일 송신 완료를 보장한다는 의미는 아니다.

### DB

- 매 guard마다 부팅 ID, DB device/inode, versionCode, SQLite schema_version을 한 번의
  ADB shell 왕복으로 읽는다. 호환되지 않는 앱 버전은 캐시가 있어도 즉시 거절한다.
- 같은 기기 객체·ADB 경로·serial·부팅 ID·파일·버전·스키마일 때 상세 열 검사 결과만
  프로세스 메모리에서 최대 30초 재사용한다. 상세 검사는 두 테이블을 하나의 읽기 전용 SQL로 묶었다.
- 식별 정보 변경·검사/쿼리 실패·만료·force 요청 시 상세 검사를 다시 한다.
  실패한 검사는 캐시하지 않는다. 재연결로 새 Device가 생성돼도 다시 검사한다.
  전송 실패도 캐시를 무효화한다. 조용한 재접속에서 식별 정보가 같으면 기존 유효 검사를 재사용한다.
- DB/행/본문/계정 이름을 새 캐시에 저장하지 않는다. DB/SQLCipher 읽기 전용 계약과
  UI 폴백 전 콘솔 잠금 검사는 유지한다. 새 CLI 프로세스 사이에 캐시를 공유하지 않는다.

### TUI

- 변경 여부를 사용해 최초 표시·실제 표시 내용 변경·입력 편집·창 크기 변경 때만 다시 그린다.
  같은 방의 동일 표시 스냅샷과 같은 상태 알림은 불필요한 다시 그리기를 유발하지 않는다.
- 한 번에 들어온 이벤트는 모두 처리한 뒤 화면을 한 번 갱신한다.
  메시지 목록의 동일 본문 여러 행과 전송 명령의 순서는 보존한다.
- curses 대기 tick을 150→50ms로 줄였다. Worker 이벤트가 화면에 나타나기까지의 대기를 줄이는
  변경이며, 키보드 입력은 기존에도 get_wch를 즉시 깨우므로 타이핑 자체가 3배 빨라진다는 뜻은 아니다.
- Worker의 새 메시지 조회 간격 2.5초는 바꾸지 않았다. 진행 중인 ADB/DB 작업도 여전히 직렬 처리한다.

### 방법과 한계

Driver 실기는 웹 콘솔을 잠시 mirror 모드로 바꾸고 매번 Friends 화면을 준비한 뒤
Chats/All 진입만 쟀다. 순서는 이전→이후→이후→이전이었다.
측정 범위는 `open_chats_tab()` 호출이며 Friends 준비·검증은 포함하지 않는다.
변경 전 8.096~8.204초, 변경 후 4.437~4.473초였다. 종료 후 virtual 모드로 복구했다.
채팅방 열기·계정 입력·실제 메시지/파일 송신은 수행하지 않았다.

DB 비교는 같은 실행 컨테이너에서 두 소스를 import해 수행했다. 계정/프로필 초기화와 기기 검색을
포함하는 새 Receiver 핸들러 및 실제 새 Python CLI 프로세스도 별도로 쟀다.
OS/ART 파일 캐시는 데워진 상태이며 VM/Android 재부팅 직후의 cold boot 측정은 아니다.
명령은 `read me --serial redroid:5555 --json`이며 최대 20개를 읽었다.
프로세스 실험에서는 CLI JSON 출력도 StringIO 메모리에서 만들고 성공 여부만 출력했다.
핸들러/상주 읽기의 전후 실제 상세 응답이 일치함을 메모리에서 비교했다.
DB 파일·WAL·사본·본문·이름·키를 결과 파일로 내보내지 않았다.
프로세스 표본 순서는 이전→이후→이후→이전을 두 번, 새 Receiver는 세 번 반복했다.
상주 읽기는 이전/이후 순서를 매번 뒤집었다. UI console lock 중에도 DB source임을 확인했다.
상주 조회 p95는 71.04→70.91ms로 거의 같아 긴 지연까지 개선됐다고 주장하지 않는다.
방 목록 전체와 새 메시지 도착/서버 동기화 시간은 측정하지 않았다.

TUI는 macOS의 실제 curses와 100×30 PTY에서 가짜 방/메시지, 전송 기능이 없는 가짜 Worker를 사용했다.
이전→이후→이후→이전 순서로 정지/이벤트 시나리오를 각각 두 번씩 실행했다.
이벤트 시나리오는 상태 알림 7개와 로컬 입력 편집만 사용했다.
CPU 시간은 정지 구간 평균 5.54→3.56ms, 이벤트 구간 9.90→8.66ms였다.
이는 짧은 구간의 작은 절대 비용이며 운영 CPU 절감률로 일반화할 수 없다.
curses는 이전에도 변경 없는 내용을 터미널에 중복 출력하지 않으므로 다시 그리기 감소를
네트워크 전송량 감소와 동일하게 보지 않는다. 표시 시점은 doupdate 호출 완료 기준이며
실제 모니터 표시나 SSH 네트워크 지연을 포함하지 않는다.

추가 Driver 모델은 UI dump 60ms, 준비 지연 80~260ms, 각 20회인 합성 재현이다.
Chats 중앙값 1,860→580ms, 자기채팅 3,410→830ms, 텍스트 송신 모델 2,500→840ms였다.
준비 확인으로 모델의 dump 수가 늘어나는 경우도 있다. 이 모델 수치를 실제 송신 속도라고 해석하지 않는다.
파일 선택기/지연 포커스/지연 입력/중복 이력/송신 확인 실패는 가짜 기기로 검증했다.
앱 버전·기기·ADB 지연에 따라 준비 확인의 비용이 고정 sleep보다 커질 수도 있다.
표본 수가 작으므로 위 감소율은 측정 사례이며 모든 명령·환경에 대한 보장이 아니다.

PYTHONPATH=src .venv/bin/python tests/benchmark_terminal.py \

실기 DB는 ADB가 연결된 컨테이너에서 위 도구에 `--part db --serial redroid:5555`를 사용한다.
두 소스 디렉터리와 도구만 전달하고 본문이 포함된 CLI 출력을 리다이렉트하지 않는다.
실기 Driver는 `--part driver-live`이며 반드시 콘솔을 mirror로 전환하고 종료 후 원래 모드로 복구한다.
virtual console lock을 우회하지 않는다. 테스트 중 사용자가 화면을 조작하면 비교를 폐기해야 한다.
